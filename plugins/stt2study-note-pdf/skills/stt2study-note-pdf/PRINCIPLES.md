# 강의 노트 PDF 생성 — 원칙 (벤더 중립)

녹취록과 교재로 **읽고 이해하는 학습 노트**를 만든다. 녹취 요약이 아니라 재구성이다.

이 문서는 어떤 AI 도구를 쓰든 동일하게 적용되는 방법론만 담는다.
"이걸 실제로 어떤 명령/문법으로 위임하는가"는 `vendors/<도구>/`를 본다.

## 대원칙 4가지

1. **녹취가 정본, 교재는 참고자료.** 강의는 슬라이드를 크게 벗어난다(실측: 핵심 용어가 녹취 40회 vs 교재 2회). 교재에 없는 강사의 실전 경험·비유·현장 사례가 노트에서 가장 값진 부분이다.
2. **줄글 인용 금지.** 발화를 재구성한다. 강사 어조가 살아야 하는 곳에만 인용 블록을 쓰되 장당 3개 이내.
3. **비유를 반드시 살려라.** 강사의 비유는 교재에 없고 이해를 가장 크게 돕는다. 각각 다이어그램 한 개 값어치다.
4. **교시 간 교차 연결을 찾아라.** 다른 교시의 개념이 사실 같은 원리임을 짚어 주는 것이 통합본의 최대 가치다.

## 아키텍처 — 왜 나누는가

하루치를 한 컨텍스트에서 다 하면 **문서 작성 단계에서 압축이 걸린다.** 실측:

| 항목 | 토큰 |
|---|---|
| 녹취 8교시 정독 | ~100,000 |
| 슬라이드 이미지 열람 | ~30,000 |
| HTML 39쪽 출력 (컨텍스트에 남음) | ~60,000 |
| 도구 결과 | ~20,000 |
| **합계** | **~210,000** → 압축 발생 |

그래서 **읽기는 독립된 작업 단위(서브에이전트/서브프로세스)에, 쓰기는 메인(오케스트레이터)에** 나눈다.
원문 10만 토큰이 메인 컨텍스트에 올라오지 않으므로 문서 작성에 여유가 생긴다.

```
Phase A · map     교시별 독립 작업 단위 (병렬 가능)
                  녹취 정독 → notes/pMM.md 구조화 노트
                  반환은 짧게 (본문은 파일에만)
                          ↓
Phase B · reduce  메인(오케스트레이터)
                  노트만 읽고 교차 연결 설계 → 파트 작성 → 조립 → 렌더
```

이 위임이 실제로 어떤 도구에서 어떻게 가능한지는 도구마다 다르다:

| 도구 특성 | 처리 방식 |
|---|---|
| 병렬 서브에이전트 위임 가능 | Phase A/B2를 각각 독립 실행 단위로 병렬 위임 |
| 서브에이전트는 가능하나 순차만 | Phase A를 교시별로 순차 위임 (병렬 대신 순서대로) |
| 서브에이전트 개념 자체가 없음 | 한 세션이 순차로 수행하되, "노트 파일부터 만들고 원문은 다시 안 읽는다"는 컨텍스트 절약 원칙만은 지킨다 |

**서브에이전트(또는 그 역할을 대신하는 단계)는 요약을 만들지 않는다.** 얇은 요약을 만들면 비유와 현장 사례가
날아가 이 작업 전체가 실패한다. 교시당 2,000~3,500자의 두꺼운 구조화 노트를 만든다.

## 입력 구조

```
dayNN/
  slides/   교재 PDF 여러 개, 파일명 자유
  audio/    p01.txt p02.txt ... (교시별 녹취)
```

교시 길이는 균등하지 않다(15~50분, 7천~2만 자). 균등 가정하지 말 것.

스크립트는 `scripts/`, 스펙/참고문서는 `references/`에 있다 (둘 다 벤더 무관, 이 폴더 기준 상대경로).

## Phase 0 · 전처리와 매칭

```bash
python3 scripts/prep.py dayNN         # 폰트 사전 체크 + 인코딩 정규화 + 인덱싱 + 등급 + 섹션 페이지
python3 scripts/idx_summary.py dayNN  # 페이지별 "한 줄 요약" 룩업 jsonl (idx_<교본>.summary.jsonl)
python3 scripts/match.py dayNN        # 교시 × 교본 매칭 행렬
```

`prep.py`는 실행 맨 앞에서 `fc-list :lang=ko`로 한글 폰트(Noto Sans CJK KR) 유무를 먼저 확인한다.
없으면 즉시 중단한다 — Phase A/B를 다 돌린 뒤 PDF 렌더 단계에서야 한글이 깨진 걸
발견하는 것보다, 비용이 큰 단계 전에 여기서 잡는 게 낫기 때문이다.

`idx_summary.py`가 뽑는 한 줄은 제목/본문 앞부분에서 **기계적으로만** 추출한다(정규식 수준,
AI 판단 아님) — `needs_review: true`로 표시된 페이지(제목이 부실하거나 이미지 위주)는
Phase A에서 실제로 그 페이지를 렌더해서 보게 되므로, 그때 본 내용이 이 기계적 추출보다
정확하다. **이 인덱스는 최초 페이지 범위 추정 전용 1회성 힌트이며, 그 이후 갱신되지 않는다** —
Phase B는 이 파일을 읽지 않고 `notes/*.md`와 `cross.jsonl`만 읽으므로 Phase A가 실제로
본 내용이 이 파일로 되돌아올 경로 자체가 없다. 갱신 로직(동시쓰기 안전장치 포함)을 추가하는
비용이, 같은 날짜를 부분 재실행할 때만 가끔 발생하는 재탐색 비용보다 크다고 판단해
의도적으로 갱신하지 않는다.

이 jsonl은 `match.py`가 전체 본문 대신 빠르게 훑을 1차 후보를 좁히는 용도이지 최종 요약이 아니다.

| 등급 | 노트 작성 |
|---|---|
| A | 텍스트 + 필요한 이미지쪽만 비전 |
| B | 매칭된 쪽 비전 |
| C | 전량 비전 — **비용 증가를 사용자에게 먼저 고지** |

한글 OCR이 필요하면 `apt-get install -y tesseract-ocr-kor`.
**단 OCR 결과는 매칭에만 쓴다** — 영문 기술용어가 심하게 깨진다(`Perplexity`→`06[0!6×1『/`).
어떤 스크립트도 tesseract를 자동 호출하지 않는다 — 필요할 때만 수동으로 돌린다.

매칭 로직(`match.py`)은 regex 패턴 매칭이 아니라 **고정 기술어 목록에 대한 단순 문자열
카운트**(`str.count()`)다. 구어체 녹취는 상위 빈도어가 전부 "이제/그래서/근데"라
빈도 대조가 무의미하기 때문에 이 방식을 쓴다.

판정:
- 70% 이상 → 대응 확실
- 30% 미만 → 교재 없이 진행된 교시. **정상이다**
- **전 교시가 전부 낮으면** 자료가 틀렸을 가능성. 진행하지 말고 사용자에게 확인

**하루 안에서도 교시마다 교본이 다를 수 있다.** 오전/오후 강사가 바뀌면 교본도 바뀐다.

### 교시별 페이지 범위 추정

`match.py`는 "이 교시가 이 교재와 매칭되는가"만 판정하지, 정확한 페이지 범위(p.A–B)까지는
주지 않는다. Phase A에 넘길 범위는 메인이 직접 정해야 한다 — `idx_<교재>.summary.jsonl`을
훑어 챕터 제목이 바뀌는 지점을 찾으면 된다. 이 범위는 후보일 뿐이니 신뢰도를 낮게 표시해서
넘기고, **Phase A가 실제 내용을 대조해 범위를 조정하도록 맡긴다** — 후보 범위가 틀려서
Phase A가 스스로 정확한 페이지를 다시 찾아낸 사례가 실제로 있었다.

## Phase A · 교시 분석

교시마다 하나씩, 도구가 지원하면 병렬로 처리한다.

**절대 규칙**
1. 요약하지 마라. 구조화하라 — 얇은 요약은 비유·현장 사례를 날려 이 작업 전체를 실패시킨다.
2. 녹취 전문을 읽어라. 앞부분만 읽고 추론하지 마라.
3. 결과는 노트 파일(`notes/pMM.md`)로 쓰고, 반환/응답은 짧게 하라.
4. 교차 후보를 반드시 채워라 — 통합본 가치의 핵심.
5. `dayNN/cross.jsonl`에는 반드시 `scripts/append_cross.py`로만 append하라(동시쓰기 안전).

**출력 스펙**: `references/chapter-note-spec.md`를 그대로 따른다. 필드를 임의로 빼지 마라.

**분량 기준**: 교시당 3,000~3,500자, 원문 대비 40% 수준(15~50분·7천~2만 자 교시 기준).
오리엔테이션·Q&A처럼 원문 자체가 짧으면 이 기준을 그대로 적용하지 말고, 없는 내용을
지어내거나 표를 억지로 채우지 않는다.

교시가 3개 이하면 위임하지 않고 메인이 직접 처리해도 된다 — 오버헤드가 이득보다 크다.

## Phase B · 통합본 작성

**원문 녹취를 읽지 마라.** `notes/*.md`만 읽는다. 노트 8개를 한 번에 다 읽으려 하면
노트가 두꺼울 때 도구 호출 출력이 잘려 일부만 읽고 통합하는 사고가 난다 — 실제로 겪은
실패다. 그래서 "연결을 찾는 일"과 "본문을 쓰는 일"을 분리한다.

### B1 · 연결 지도와 목차 재설계 (메인)

1. `dayNN/cross.jsonl`만 읽는다. 노트 전체를 열 필요 없다.
2. 같은 원리가 반복되는 지점을 짚어 "하루를 관통하는 한 문장"을 정한다.
3. **주제 기반으로 장(章) 목차를 다시 짠다 — 교시 1개를 장 1개로 기계적으로 매핑하지 않는다.**
   결과를 `dayNN/outline.md`에 적는다.
4. 실제로 연결될 항목만 골라 연결 지도를 짧게 정리한다. 지어내지 않는다 — `cross.jsonl`에
   근거가 없으면 넣지 않는다.
5. 다이어그램 대상 페이지를 노트의 `## 교본 도해 판정` 표 기준으로 정리한다.
6. 표지의 "하루의 흐름"을 메인이 직접 쓴다.

### B2 · 파트 작성

`dayNN/outline.md`의 장 구성 기준으로 파트를 나눈다. 파트마다 하나씩, 도구가 지원하면
병렬로 처리한다. 원문 녹취는 열지 않고, 담당 노트와 (B1이 그 파트에 해당하는 항목만
추려 준) 연결 지도만 본다. 도해는 `{{key}}` 플레이스홀더로 `<img>` 태그 안에만 남긴다 —
밖에 맨몸으로 쓰면 base64 텍스트가 그대로 인쇄되는 사고가 난다.

교시가 3개 이하거나 파트가 1~2개뿐이면 위임하지 않고 메인이 직접 써도 된다.
이때도 outline.md 작성은 생략하지 않는다.

구성·박스 사용법은 `references/document-structure.md`, 다이어그램 규칙은
`references/diagram-rules.md`, STT 교정은 `references/stt-corrections.md` 참조.

## Phase C · 렌더와 검증 (메인)

```bash
python3 scripts/slide.py 교재.pdf 51 --view                    # 먼저 확인
python3 scripts/slide.py 교재.pdf 51 S51                       # 도해 추출 — 기본은 crop 없이 페이지 전체
python3 scripts/build.py out/dayNN.pdf part1.html part2.html part3.html
python3 scripts/verify.py out/dayNN.pdf
```

크롭 좌표(`290,290,1400,810`처럼 뒤에 붙이는 인자)는 한 페이지에 무관한 도해가
여럿 섞여 분리해야만 할 때만 예외적으로 쓴다. 눈대중 좌표가 어긋나면 최종본에서
그림이 깨지거나 잘리는 사고로 이어진다 — 자세한 사유와 절차는
`references/diagram-rules.md`의 "크롭 대신 전체 장표를 그대로 가져온다" 참조.

`verify.py`가 만든 컨택트 시트를 **반드시 육안 확인한다.** 한글 깨짐·누락 / SVG 요소
겹침 / 표가 페이지를 가로지름 / 빈 페이지 / 도해 캡션과 실제 그림 불일치.

**콘텐츠 완결성도 시각 확인과 별개로 반드시 대조한다** (`verify.py`가 아래 두
항목의 개수를 자동으로 세서 출력한다):

1. 노트의 `## 교본 도해 판정`에서 원본 사용(`✅`)으로 표시한 개수 vs 최종본의
   `<img src="data:image...">` 개수. 적으면 원본 대신 직접 그림으로 임의 대체한
   것이다 (`references/diagram-rules.md` 위반) — 원인을 밝히고 고치기 전에는
   넘어가지 않는다.
2. 노트의 `## 현장 사례`에 실제 내용이 있는 항목 수 vs 최종본의 `.example` 박스
   개수. 적으면 강사의 실제 사례가 통합 단계에서 요약되거나 빠진 것이다
   (`references/document-structure.md`의 "강사의 실제 예시 박스" 위반).

두 항목 다 숫자가 안 맞으면, 왜 안 맞는지 스스로 판단해 조용히 넘어가지 말고
사용자에게 먼저 알린다 — 의도적 제외(예: 같은 사례 중복)라면 그 이유를 밝히고,
아니라면 빠진 것을 복원한다.

## Phase D · OKF 변환 (사용자가 원할 때)

```bash
python3 scripts/build_okf.py <project> dayNN
```

`<project>`는 사람이 부르는 프로젝트 이름 — 묻지 않고 임의로 짓지 마라.
자세한 내용은 `references/okf-spec.md` 참조.

## 산출물

**① 최종**: `out/dayNN.pdf`
**② 중간 산출물** (재사용/누적, OKF 변환 대상): `notes/pMM.md`, `cross.jsonl`, `outline.md`,
`idx_<교재>.json`, `idx_<교재>.summary.jsonl`, `diagrams.json`, `glossary.md`
**③ 입력 자료** (원본, OKF 변환 대상): `audio/pMM.txt`, `slides/*.pdf`
**④ 작업용 임시 파일** (OKF 변환 대상 아님): `part*.html`, base64 캐시, 컨택트 시트

②③만으로 ①을 다시 만들 수 있어야 한다는 게 이 구분의 전제다.

## 사용자에게 확인할 것

- 모든 교시의 교본 매칭이 실패했을 때
- 등급 C 판정으로 비전 비용이 크게 늘 때
- 첫 교시 샘플 완성 후 형식 확정
- OKF 변환 시 프로젝트 이름을 모를 때
- OpenViking 등에 업로드할 때 원격에 그 프로젝트 이름이 없으면
- Phase C 콘텐츠 완결성 검증에서 도해·현장 사례 개수가 안 맞을 때

나머지는 묻지 말고 진행한다. 중간 판단이 틀렸으면 먼저 정정하고 넘어간다.
